§01 · Executive vision

One platform: SAP supplies governed data, AGENT SRIA supplies governed action

The first cycle delivered a safe, narrow, deterministic dashboard generator. The second cycle turns it into an enterprise agent that can understand an objective, plan, call approved tools, observe real results, recover, and explain its work — while SAP remains the single source of truth and the backend remains the only enforcement boundary.

Pillar A · SAP Intelligence & Enterprise Data Foundation

Move from synthetic in-memory records to a governed, source-agnostic data-product layer with a versioned finance semantic model, then connect a verified S/4HANA API through a BTP Destination. Live SAP access is gated on facts only the SAP and Finance teams can supply.

Pillar B · AGENT SRIA

Replace the single-tool, keyword-driven flow with a bounded Plan–Act–Observe runtime: model-assisted planning validated by the backend, a governed tool platform, closed-loop observation, context management, human approval and full auditability.

Experience · Transparency & control

Every agent capability gets a finance-readable UI: interpretation, plan preview, live timeline, tool activity, evidence, approvals, memory controls. Not a chatbot — an agent workspace.

Non-negotiable engineering rules (carried into every phase)

Truthfulness
  • No “live SAP” claim while data is synthetic.
  • No “autonomous agent” claim until the agent-claim checklist (§08) passes.
  • No multi-agent claim before it is built and tested.
  • Architecture documents are not implementation evidence.
Safety & control
  • Backend is the enforcement boundary; the model never gets SQL, credentials or open network.
  • Model-proposed tool arguments never bypass backend validation.
  • Tenant and user authorization on every call; human approval for sensitive actions.
  • Every agent action observable and auditable.
Correctness & restraint
  • Deterministic financial arithmetic (ADR-003 stands).
  • No raw financial records as agent memory.
  • Mock / local / pilot / production environments always distinguishable.
  • No ontology, vector store, graph DB or microservices without a concrete trigger.

Trust boundaries
  1. Browser ↔ CAP: browser is untrusted; identity and tenant come only from the validated token.
  2. CAP ↔ LLM provider: outbound only, redacted context, structured output, output treated as untrusted data.
  3. CAP ↔ SAP via Destination: technical or propagated principal; read-only; bounded queries.
  4. Tool output ↔ model: tool results are untrusted content (indirect injection).
Persistence boundaries
  • Persisted: specs, runs/steps/events (metadata + digests), approvals, conversations (compacted), explicit user memory, semantic model, audit.
  • Ephemeral: raw SAP rows, full tool outputs, model prompts containing figures, working memory.
  • Never: credentials, tokens, raw journal lines, chain-of-thought.
Human-approval boundaries
  • Plan preview for multi-step or costly runs.
  • Approval for any state-changing or outward-facing tool (share, export, org-wide publish, delete).
  • Approval when a replan expands scope (new entities, wider periods, new tools).
  • Write-back to SAP: denied by policy in Phase 2.

    Authentication model: decision required, not assumed

    Technical communication user (one least-privilege read-only identity per tenant/system) is the simplest and is the default plan for the pilot. Principal propagation (the end user’s identity reaches S/4HANA so SAP authorizations apply per user) is stronger but needs IAS/XSUAA trust, Cloud Connector or certificate mapping and SAP-side role design. Decision D-05 belongs to the SAP security owner; the data-product layer is designed so either works, and the agent’s authorization never depends on which is chosen.

    Why a data-product layer, not a data lake

    Tools should ask for “financial performance for entities X, period Y, dimensions Z” — never for journal-entry tables. A CAP domain service owning that contract isolates SAP structure from the agent, carries lineage and quality flags, and lets BW, ECC or non-SAP sources be added behind the same contract. ADR-002 (on-demand transient retrieval, no replication) remains in force; a curated store is introduced only if measured latency or volume demands it.

    §08 · Pillar B — AGENT SRIA

    What AGENT SRIA is, what it is not, and what must be true before we call it an agent

    AGENT SRIA is the orchestration layer between a user’s business objective and the governed capabilities of the platform. It is not an LLM with tools attached: it is a bounded runtime that owns state, budgets, validation and observation, using a model for the parts that need language understanding and judgement.

    AGENT SRIA is…
    • A goal-driven runtime: objective → plan → act → observe → evaluate → revise or finish.
    • Model-assisted, backend-governed: the model proposes understanding, plans and wording; the backend validates, authorizes, executes and verifies.
    • Stateful: every run is a persisted state machine with budgets, events and a final status.
    • Transparent: plans, tool calls, evidence and approvals are structured data shown to the user.
    • Extensible: new tools and skills are registered through manifests, not code paths in the loop.
    AGENT SRIA is not…
    • A chatbot that answers from model memory.
    • An unbounded autonomous loop; every run has hard budgets and stop conditions.
    • A database or SAP client: it has no SQL, no credentials, no raw OData, no network of its own.
    • A calculator: numbers come from deterministic tools; narratives must be numerically grounded.
    • A multi-agent swarm. Specialist agents are a future option with an explicit trigger (§22).

      §10 · Context & memory

      Carry what matters, compact what doesn’t, persist almost nothing sensitive

      The model never receives unlimited history. A Context Manager assembles each request from budgeted sections, compacts older turns into a structured summary, and stores only references and non-sensitive parameters. Raw financial records are never general-purpose memory — numbers are re-fetched through authorized tools and re-checked at use.

      Context assembly budget (illustrative tokens for one model call)

      Memory tiers

      Compaction algorithm
      1. Trigger when assembled context exceeds ~70% of the section budget or after N turns.
      2. Keep verbatim: system policy, active task state, the last 2–3 turns, pinned facts (confirmed entity, period, currency, approvals).
      3. Summarize older turns into a structured record: goals, confirmed parameters, decisions, open questions, artifact references (run IDs, spec IDs) — not free prose.
      4. Validate the summary deterministically: schema check, no numeric amounts outside an allow-list of digests, no identifiers from other tenants.
      5. Store the summary with source-turn range and version; the raw turns age out per retention policy.
      Never in context or memory
      • Raw journal lines, GL-level line items, document text with PII.
      • Credentials, tokens, Destination details, internal URLs.
      • Another tenant’s or user’s data (every read keyed by organization and user).
      • Chain-of-thought; only structured plan purposes and decision summaries are retained.
      • Unredacted tool output beyond the declared output-digest fields of its manifest.
      §11 · Tools & actions

      A governed tool platform: every tool is a manifest the backend can enforce

      The candidate tools below are capabilities, not a commitment to expose all of them. Each has a purpose, schemas, permissions, risk, approval rule, idempotency, timeout/retry, audit and failure behaviour. The LLM never sees a database handle or an SAP credential; it names a tool and proposes arguments, and the backend decides.

      Tool call lifecycle (every call, every time)

      1 · Propose

      Model/planner names tool + args.

      2 · Validate

      Manifest exists; args pass Zod; entities exist in semantic layer.

      3 · Authorize

      User roles, tenant, data scope — user’s authority, not the agent’s.

      4 · Policy

      Risk × role × environment → allow / approve / deny.

      5 · Execute

      Idempotency key, timeout via abort, retry by error class.

      6 · Observe

      Output schema + plan-expectation checks.

      7 · Digest & audit

      Redacted digest to context; audit event written.

      Tool manifest (proposed contract, TypeScript sketch)

      interface ToolManifest<I, O> {
  name: string; version: string; family: 'finance'|'analytic'|'dashboard'|'platform';
  purpose: string;                       // shown to user in plan preview
  input: ZodType<I>; output: ZodType<O>;
  permissions: Role[];                   // checked against the *user*
  risk: 'low'|'medium'|'high';           // feeds the policy table
  approval: 'never'|'on-share'|'always'; // policy may only tighten this
  idempotency: 'pure'|'keyed'|'unsafe';  // 'unsafe' tools are never retried
  timeoutMs: number; retry: { max: number; on: ErrorClass[] };
  dataClass: 'metadata'|'aggregate'|'sensitive';
  outputDigest: (o: O) => Digest;        // the only part allowed into context/memory
  audit: { action: string; fields: string[] };
  failure: { userMessage: string; recoverable: boolean };
  execute(i: I, ctx: ExecutionContext, signal: AbortSignal): Promise<O>;
}

      §12 · Security & governance

      Defence in depth for an agent that can act

      Agent-specific threats are layered on top of the existing controls. The guiding rule: the agent has no authority of its own — it acts with the requesting user’s authority, bounded by tool manifests and policy, so it can never be a confused deputy that exceeds what the user could do.

      Isolation: which mechanism, and do we need it?

      Sandboxing is introduced only where a genuine risk exists. Today the agent executes no model-generated code, so container sandboxing is not needed; tool-level authorization, tenant isolation and data-access boundaries are the controls that matter.

      §13 · Semantic layer

      Business meaning as governed, versioned data — shared by the agent and the calculators

      The current registry is four hard-coded definitions in packages/contracts. The semantic layer turns meaning into versioned tables that the planner, the intent prompt, the calculation engine and the UI glossary all read — so a metric definition has exactly one home and one approval trail.

      How the agent and the calculators use it
      • Agent: resolves terms (“sales”, “opex”) to approved metric IDs; lists what is answerable; refuses undefined metrics with alternatives; cites definition + version in answers.
      • Calculators: read formula dependencies (a DAG, cycle-checked), aggregation and currency rules; results carry metric version and lineage.
      • Governance: only APPROVED versions execute; an owner and approver are recorded; changing a formula creates a new version, never an edit in place.
      Metric growth rule

      No new finance metric is invented by engineering. Candidates (e.g. cost-of-goods-based gross profit, opex by category) enter as PENDING_REVIEW with a proposed SAP mapping and become executable only after Finance sign-off and reconciliation against the live system.

      §21 · Testing & acceptance

      Agent testing needs more layers than a CRUD application

      Probabilistic components are tested with deterministic harnesses first (replay, golden data, fault injection), then with live models on a schedule, with safety invariants asserted at the HTTP layer where the security boundary actually is.
