// 1. CDS Model (apps/cap/db/dashboard.cds)
entity Dashboards : cuid, managed {
  organization : Association to Organizations not null;
  title        : String(150) not null;
  ownerId      : String(100) not null;
  isArchived   : Boolean default false;
}

// 2. CDS Service API (apps/cap/srv/dashboard-lifecycle-service.cds)
@path: '/api/v1/lifecycle'
service DashboardLifecycleService {
  action SaveDashboard(title: String(150), specJson: LargeString not null) returns { dashboardId: UUID; status: String; };
}

// 3. CAP Handler + CQL Query (apps/cap/srv/lib/repositories/dashboard-repository.ts)

Section 03 · Core Knowledge Inventory

12 SAP BTP & CAP Concepts You Cover by Executing This Codebase

Each card explains what the concept is in SAP, how it works in real life, and exactly where it lives in your repo.

1

CDS Domain Modeling (db/*.cds)

How it works: Instead of writing raw SQL CREATE TABLE scripts, SAP CAP uses Core Data Services (.cds). Using cuid adds an auto-UUID primary key ID; managed adds createdAt, createdBy, modifiedAt, modifiedBy automatically. Association links tables loosely; Composition expresses parent-child ownership (like Dashboards owning DashboardSpecs).

2

CDS Service Projections, Actions & Functions

How it works: In srv/*.cds, entity X as projection on my.X safely exposes DB tables as OData/REST APIs without exposing raw schema internals. action is used for POST operations that change state or run workflows (SaveDashboard, ExecutePlan), while function is used for read-only GET queries (ListDashboards(), getApprovedMetrics()).

3

cds.ApplicationService Custom Handlers

How it works: Every .cds service file automatically pairs with a same-named .ts/.js file (e.g., ai-service.cds + ai-service.ts). Inside init(), this.on('ActionName', handler) hooks your TypeScript code into CAP's HTTP/OData pipeline, giving you req.data, req.user, and req.error(code, msg).

4

CQL (CAP Query Language)

How it works: SELECT.from(...), INSERT.into(...), and UPDATE(...) in dashboard-repository.ts are fluent JavaScript query builders. CAP compiles CQL into SQLite SQL locally and SAP HANA SQL in production automatically—making your code database-portable.

5

CAP Environment Profiles (.cdsrc.json)

How it works: CAP switches infrastructure using profiles. Under [development], requires.db.kind = "sqlite" uses local sqlite.db and mock auth. Under [production], CAP switches to "hana" and "xsuaa" without changing a single line of TypeScript service code.

6

CAP Server Bootstrap & Custom Express Routes

How it works: CAP runs on top of Express.js. In apps/cap/srv/server.js, cds.on('bootstrap', app => ...) lets you attach standard Express middleware (CORS headers) and custom REST endpoints like GET /health before CAP mounts its OData routes.

7

SAP XSUAA RBAC (xs-security.json)

How it works: SAP BTP's OAuth2 authorization server uses a 3-tier security hierarchy: Scopes ($XSAPPNAME.FinanceAnalyst) → grouped into Role Templates (FinanceManager) → assigned to business users via Role Collections (SriaFinanceManager) in BTP Cockpit. At runtime, AuthGuard checks req.user.is('FinanceManager').

8

Server-Side Multi-Tenant Isolation

How it works: In SaaS BTP apps, multiple customer companies share one runtime. AuthGuard extracts the tenant ID from the verified token (never trusting client headers alone), and DashboardRepository injects organization_ID into every query so Tenant A can never read Tenant B's dashboards.

9

CAP Build Artifacts (cds build → gen/srv)

How it works: Running npm run build --workspace=apps/cap compiles all .cds models into a single Core Schema Notation file (csn.json) and generates OData v4 XML $metadata files inside apps/cap/gen/srv/ ready for Cloud Foundry deployment.

10

SAP BTP Multi-Target Application (mta.yaml)

How it works: Instead of deploying frontend, backend, security, and destinations separately, mta.yaml packages sria-cap-srv (Node.js) + sria-web-ui (HTML5 static) + sria-xsuaa + sria-destination into one deployable .mtar archive for Cloud Foundry.

11

BTP VCAP_SERVICES & Destination Concept

How it works: On SAP BTP Cloud Foundry, credentials are never placed in code. When you bind sria-xsuaa or sria-destination to an app, BTP injects connection credentials into the container's VCAP_SERVICES JSON env variable, which CAP reads automatically on startup.

12

SAP S/4HANA OData Side-by-Side Extension Pattern

How it works: This app demonstrates SAP's recommended "Clean Core / Side-by-Side Extension" pattern: never modify S/4HANA core ABAP code; instead, query standard SAP OData CDS views (I_JournalEntryItemBasic) transiently over HTTPS from CAP on BTP, and build AI/analytics outside S/4HANA.
